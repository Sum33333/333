## 二、泽慧系统的完整 Pipeline（整理）

泽慧同学实现的是：**频谱（STFT）瀑布图接收 → 滑窗切图 → 调用检测服务 → 把检测框映射回频谱 → 发布分割结果**。  
检测模型本身以**独立子进程**形式存在，分割端只通过标准输入输出交换信息。

### 2.1 总览图

```text
[频谱发布端]
   通过网络端口推送 STFT 数据
   （本机常见地址：tcp://127.0.0.1:5560）
            │
            ▼
[分割接收端]  segmentation_engineer_receiver.py
   ┌─────────────────────────────────────────┐
   │  1. 接收并累计瀑布图帧                   │
   │  2. 按窗口大小 / 步长切出一段窗口         │
   │  3. 窗口上色，存成 PNG 图片               │
   │  4. WindowSegmenter 调用 DetectionClient │
   │  5. 把像素框映射回频谱坐标                │
   │  6. 发布分割结果（常见端口 *:5571）       │
   └─────────────────────────────────────────┘
            │
            │  子进程管道通信
            │  （启动 detection_server.py）
            ▼
[检测服务端]  detection_server.py（可替换为适配器）
   ┌─────────────────────────────────────────┐
   │  启动后先输出一行 ready（JSON）           │
   │  循环读取：图片绝对路径 → 推理 → 输出框   │
   │  读到 EXIT 则退出                        │
   └─────────────────────────────────────────┘
```

### 2.2 各模块职责

| 模块 | 典型位置 / 名称 | 做什么 |
|------|-----------------|--------|
| 频谱源 | 上游采集 / STFT 发布程序 | 持续推送频谱帧 |
| 分割主程序 | `/home/sribd/111/segmentation_engineer_receiver.py` | 收频谱、画瀑布、切窗、调检测、发结果 |
| 窗口分割器 | 类 `WindowSegmenter` | 窗口管理 + 调检测 + 坐标映射 |
| 检测客户端 | 类 `DetectionClient` | 用子进程启动检测脚本，发图路径、收 JSON |
| 检测服务 | `~/jetson/detection_server.py` | 加载模型并推理；对外协议固定 |
| 结果发布 | 分割端内网络发布 | 把分割事件发给下游（界面或其他程序） |

### 2.3 检测接口协议（不可随意改）

这是整条流水线里“新旧模型对接”的关键卡口。

**启动参数（示例）：**

```text
python detection_server.py
  --weights  权重路径
  --model    模型名
  --threshold 0.1
  --imgsz 672
  --device cuda:0
```

**运行时通信：**

| 方向 | 内容 | 含义 |
|------|------|------|
| 分割端 → 检测端 | 一行图片绝对路径 | 请检测这张 STFT 窗口图 |
| 分割端 → 检测端 | `EXIT` | 结束检测进程 |
| 检测端 → 分割端 | `{"status":"ready", ...}` | 模型/服务已就绪 |
| 检测端 → 分割端 | `{"status":"ok","detections":[...]}` | 本张图的检测结果 |
| 检测端 → 分割端 | `{"status":"error","message":"..."}` | 出错说明 |

**每个检测框必须包含的字段：**

`x1, y1, x2, y2, label, score`  
（像素坐标；标签常见如 signal / burst；分数为置信度）

**图片含义：** PNG 彩色图，一般缩放到约 672×672；来自一段 STFT 窗口上色；轴对应频率格点 / 时间帧，颜色对应能量强弱。

## 三、上周为什么 mmdet 没法跑通（实验与结论）

说明：新权重按 OpenMMLab 检测体系训练/导出，正常推理链路是 **PyTorch + mmcv + mmengine + mmdet**。  
上周在 Jetson（ARM 架构）上的阻塞点主要在 **mmcv（带 CUDA 扩展）装不上**，导致 mmdet 无法完整工作，也就无法用 `epoch_100.pth` 做真实推理。

### 3.1 实验环境

| 项目 | 情况 |
|------|------|
| 机器 | NVIDIA Jetson（架构 aarch64 / ARM） |
| Python 环境 | conda：`usrp_dev`，Python 3.11 |
| 目标组合 | 尝试 `mmcv==2.1.0` + `mmdet`（与常见 3.x 要求匹配） |
| 权重 | `/home/sribd/111/epoch_100.pth` |
| 配置 | Faster R-CNN + Swin 一类 IQ/二分类配置（导师提供） |

### 3.2 分步实验结果

| 步骤 | 现象 | 结果 |
|------|------|------|
| 安装 PyTorch | `cuda` 可用 | 通过 |
| 安装 mmengine | 可 import | 通过 |
| 安装 mmdet | 包装上，但依赖完整 mmcv | 半通过 |
| 寻找官方带 CUDA 的 mmcv 现成包 | 主要为 x86 平台提供；ARM 上无匹配现成轮子 | 只能源码编译 |
| 源码编译 mmcv（带 ops） | 前期缺头文件（如 `nv/target`）；补齐 CCCL 后继续编译 | 仍失败 |
| 最终编译错误 | CUDA 编译器与工具链头文件不兼容；并存在版本不一致提示（环境 nvcc 约 13.3，PyTorch 侧约 13.0） | **失败** |
| 验证 mmdet 可用性 | 适配器启动日志：`No module named 'mmcv'` | mmdet 链路不可用 |
| 另一套可运行方案 | 用协议兼容的模拟检测适配器接原入口 | 分割端可 `detector ready` |

### 3.3 关键报错（摘要）

1. **平台限制**  
   ARM 板没有与桌面 x86 相同的现成 mmcv（CUDA）安装包，必须本地编译。

2. **编译依赖不齐（已部分解决）**  
   曾出现找不到 CUDA/CCCL 相关头文件；安装对应组件后可越过该点。

3. **最终失败点（未解决）**  
   编译 CUDA 扩展时报告：编译器与 toolkit 头文件不兼容；同时 PyTorch 编译所用 CUDA 小版本与当前 nvcc 不一致。  
   → `Building wheel for mmcv` 失败，完整 mmcv 未安装成功。

4. **连锁后果**  
   - 没有完整 mmcv → mmdet 的 CUDA 算子（如 ROI 相关）不可用  
   - 无法按标准检测接口加载并推理 `epoch_100.pth`  
   - 分割流水线前端可通，但“真实检测”这一环缺依赖

### 3.4 结论性说明

1. **不是分割流水线本身坏了。**  
   泽慧系统的收频谱 → 切窗 → 调检测 → 回框 → 发布，协议与主流程是清楚的；板端已验证能拉起检测子进程并收到 ready。

2. **卡住的是“真实检测依赖”。**  
   在本机 ARM + 当前 CUDA/PyTorch 组合下，**带 CUDA 扩展的 mmcv 源码编译失败**，因此 mmdet 完整推理跑不通。

3. **权重文件本身不等于能直接推理。**  
   `epoch_100.pth` 需要匹配的检测框架与算子支持；缺 mmcv 时，不能按现有 mmdet 路径调用该权重。

4. **已验证可行的路径。**  
   在不改协议字段的前提下，用兼容旧接口的适配器先保证联调；待板端获得匹配的预编译 mmcv（或统一 CUDA 版本后再编译成功），再切换为权重真实推理。

5. **出框还依赖频谱源。**  
   即使检测服务 ready，若无 STFT 推流（5560），分割端仍会 `recv=0`，看不到窗口检测结果——这与 mmcv 问题是两件独立的事。
